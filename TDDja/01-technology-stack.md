# 技術スタックの選定方針と経緯

## 1. 文書の位置づけ

Ogre Throne の初期技術スタックについて、採用した構成、選定理由、比較した候補を記録する。
対象は、このプロジェクトの初期構築から Windows の標準コンパイラーを Clang に変更した段階までとする。

採用方針と、選定時の評価・期待を区別する。
検討経緯に登場する候補や機能は、それだけで採用・実装を指示するものではない。
［補足］は会話と実装から整理した説明であり、独立したユーザー決定として扱わない。

［補足］実装状況の参照点は、親リポジトリの `0686d21` と、OGRE Next の `throne-dev` ブランチ上の `3aac07eba`。
この文書は選定時の判断記録であり、各ライブラリの最新版の機能一覧や性能比較ではない。

## 2. 全体方針

完成済みのゲームエンジンを土台にするのではなく、C++／C の OSS ミドルウェアを組み合わせてゲームエンジンを構築する。
描画基盤には、3D 表示だけでなくゲーム用途に必要な機能が充実したものを求める。

グラフィックス API は Vulkan を中心とし、独自の D3D12 対応を採用要件にしない。
Apple デバイスについては、Vulkan を MoltenVK 経由で利用する方向とする。

［補足］既存の経験を活用できること、必要な機能を後から実装できること、ライブラリの責務を分けられることを重視した構成である。
すべての機能が標準装備されていることや、現時点のデモの見栄えだけでは選ばない。

### 2.1. 採用構成

| 領域 | 採用する技術・方針 | 主な判断 |
| --- | --- | --- |
| 描画 | OGRE Next、Vulkan | OGRE の利用経験と、ゲーム向け描画基盤としての機能を重視 |
| 物理 | Box3D | クロスプラットフォーム決定性を標準の方針とする点を重視 |
| スクリプト | L^ | プロジェクトのスクリプトエンジンとして採用 |
| エディター UI | Dear ImGui | エディター向け UI の基盤として採用 |
| インゲーム UI | Colibri GUI | OGRE と組み合わせる UI・文字描画の基盤として採用 |
| 音声再生 | SoLoud | 必要な形式への対応と、ライセンス・組み込みの扱いやすさを重視 |
| 空間音響 | Steam Audio | 壁による遮蔽・透過と、音の反射を実現するために採用 |
| Windows 標準コンパイラー | Clang（clang-cl） | Clang を標準とする |
| Windows 互換性確認 | MSVC | 別プリセットでビルド・テスト可能な構成を残す |
| 依存管理 | 親リポジトリ配下の Git submodule | プロジェクトで使う依存を固定コミットで管理する |

［補足］現在のブートストラップは C++17 を使用し、Box3D などの C ライブラリも一緒にビルドする。
ビルド構成は CMake Presets で管理する。

## 3. 描画基盤

### 3.1. Vulkan を中心にする理由

Windows で D3D12 が使えること自体を利点とは扱わない。
背景には、Unity の D3D12 環境でシェーダーのプリウォームが期待どおりに動かなかった経験がある。
その際は、ロード画面の裏でプレハブを読み込み、1 フレーム表示してから破棄する対処が必要になった。

この経験から、対応 API を Vulkan に絞り、D3D12 を使わずに済む構成を好む。
OGRE Next の D3D12 非対応についても、選定上の欠点とは扱わなかった。
関心のない API の対応に開発リソースが割かれにくいことへの期待もあった。

［補足］この期待は、OGRE 開発側が D3D12 を採用しない理由を確認した結論ではない。
また、Vulkan を選ぶだけでシェーダーやパイプラインの初回生成による停止が解消する、という判断でもない。

### 3.2. OGRE Next、Filament、VSG の比較

| 候補 | 選定時に評価した点 | 採否につながった判断 |
| --- | --- | --- |
| OGRE Next | 以前 OGRE を使用しており、慣れと思い入れがある。ゲーム向けの機能に期待できる | 採用。標準の Deferred レンダラーがすぐ使えない点は懸念として認識した |
| Filament | デモの見た目と PBR の品質が魅力的。最後まで有力な候補だった | ゲーム基盤としての適合性を重視し、最終的には OGRE Next を選択した |
| OpenSceneGraph／VulkanSceneGraph | 3D 表示が必要なツールの基盤としては有用という評価 | 検討した標準パイプラインが求める Clustered Forward の条件を満たさないとの評価から見送った |

OGRE Next を使う商用エンジンとして Skyline を見つけ、その見た目を OGRE Next の可能性を示す材料として評価した。
Skyline 自体を本プロジェクトの土台として採用したわけではない。

### 3.3. Forward／Deferred とゲーム向け機能

Deferred レンダリングの有無を確認したのは、多数のライトを扱える実用的な描画基盤を求めていたためである。
ただし、Clustered Forward が実用レベルなら、それを採用することは許容する。
Deferred が今後衰退すると決めつけて選んだわけではない。

選定時には、Forward+／Clustered Forward に加えて、シェーダー・PSO のウォームアップとディスクキャッシュ、Alpha Hashing／Alpha-to-Coverage の説明が採用を後押しした。

［補足］これらは選定時に期待した機能であり、Ogre Throne 側で導入・検証を完了した機能の一覧ではない。
現在の構成ではシェーダー・PSO のスレッドコンパイル設定を有効にしているが、ウォームアップ方針、キャッシュの永続化、Alpha Hashing の設定は未実装である。

### 3.4. 半透明と時間方向の描画

半透明については描画順の問題も認識しており、許容できるアーティファクトの範囲で、UE の `DitherTemporalAA` のようにディザと時間方向の蓄積を使う方法を評価している。
これは、通常のアルファブレンドだけで解決することを必須としない、という選好である。

UE の時間方向 AA を評価した背景には、AA 単体ではなくポストプロセス全体との統合がある。
特に Panini 投影後の画面中央の解像感を気にしており、低解像度入力からのアップスケールと、投影後の解像度不足を補う設計は区別して検討した。
Unity の STP も話題に上がったが、それを Ogre Throne に採用する決定はしていない。

時間方向 AA・アップスケール・ディザ半透明の具体的な方式は STK-01 として保留する。

### 3.5. glTF と実行時アセット

glTF 2.0 に対応することだけで、Filament を優位と判断しない。
制作・交換用フォーマットとしての有用性と、ゲームへ同梱する実行時データ形式の効率は分けて考える。

実行時に glTF をそのまま読み込むことより、用途に適したバイナリシリアライズ方式を持つことが利点になる、という評価である。
OGRE 向けの Blender 拡張があることも、制作ツールからデータを出力する経路への懸念を小さくする材料だった。

［補足］この評価は、独自形式が必ず高速・省メモリーになるという計測結果ではない。
インポート経路、変換処理、配布形式の具体化は STK-02 として保留する。

## 4. 物理とスクリプト

### 4.1. Box3D を選ぶ理由

物理エンジンの主な比較対象は Jolt と Box3D だった。
Jolt は、車両、ソフトボディ、ラグドール連携など、機能の広さで魅力があった。
一方、Box3D は新しく、実績や第三者の評価がまだ少ないことを懸念した。

検討中に、Jolt にも条件・制限付きの決定的シミュレーション機能があることを確認した。
「Jolt には決定性がないから Box3D を選ぶ」という結論ではない。

最終的には、Box3D がクロスプラットフォーム決定性を標準の方針としている点を重視し、新しさに伴う不確実性を受け入れて採用する。
ラグドールやソフトボディは、必要なら剛体物理の上にゲームエンジン側で構築するという考えを持っており、内蔵機能の多さを最優先にはしない。

［補足］決定性には入力・操作順やビルド設定を揃える条件がある。
Box3D とシミュレーションには fast-math を適用しない。
現在のテストが確認しているのは、同一ビルドで 180 ステップを再実行した際の位置の一致であり、異なる OS・CPU・コンパイラー間の一致を実証したものではない。

### 4.2. L^

スクリプトエンジンには L^ を採用する。

［補足］この選定会話では、代替言語との詳細な比較理由は記録されていない。
既存の L^ をゲームエンジンへ組み込むことを初期構成の前提とし、現段階では VM の生成・破棄をスモークテストで確認している。
ゲームオブジェクトなどの API をスクリプトへ公開する設計は、VM 初期化とは別の実装範囲になる。

## 5. UI・文字・ベクター描画

エディター UI は Dear ImGui、インゲーム UI は Colibri GUI を基盤とする。
Colibri はデバッグ表示専用という位置づけではなく、ゲーム内 UI の候補として検討・採用した。

Colibri のスクリーンショットの見た目だけでは積極的に使いたくなるものではなかったが、フォント機能が要求を満たすなら採用に値する、と評価した。

文字描画では、通常サイズの文字をすべて SDF にすることを求めない。
小さいサイズでは従来のラスター描画で十分という考えがあり、UE でその方式に困っていないことも背景にある。
重要なのは日本語を描画できることと、事前生成済みテクスチャだけに依存せず、実行時にグリフを複数のテクスチャへキャッシュできることである。
Colibri のフォントシステムは、この要求に対応する基盤として評価した。

SVG 対応も必要と考えている。
検討では「ThorVG の CPU 描画 → サイズ別キャッシュ → OGRE テクスチャ → Colibri」という経路を挙げたが、形状をポリゴンへ変換して描画する方法にも関心がある。
SVG ライブラリや描画方式の採用は STK-03 として保留する。

［補足］現時点では Dear ImGui と Colibri の初期化までを実装している。
UI の描画・入力、実際の日本語 UI、SVG 表示を製品機能として結線した状態ではない。

## 6. 音声再生と空間音響

### 6.1. 必要な機能

音声ファイルは WAV／Ogg／MP3 に対応していれば十分とする。
単純な左右のパンだけでなく、壁越しの音の変化や音の反射を実現するため、Steam Audio を採用する。

### 6.2. SoLoud と OpenAL Soft の比較

| 構成案 | 評価 | 結論 |
| --- | --- | --- |
| OpenAL Soft ＋ Steam Audio ＋ デコーダー | OpenAL Soft の実績を評価。一方、LGPL である点と音声形式への対応を別途用意する点を難点とした | 今回は見送る |
| SoLoud ＋ Steam Audio | 必要なファイル形式に対応し、SoLoud のライセンス・組み込みの扱いやすさを評価。空間音響は Steam Audio に担当させられる | 採用する |

SoLoud 自身の 3D サウンド機能だけで品質を判断せず、Steam Audio と組み合わせて求める空間音響を得る方針とする。
OpenAL Soft の品質が不足している、という理由で見送ったわけではない。

### 6.3. 役割分担と実装範囲

Steam Audio 単体でファイル読み込みからデバイス再生まで完結する、という構成ではない。
SoLoud をデコード・再生管理・ミキシング・出力の基盤とし、Steam Audio に音響シミュレーションと PCM への音響処理を担当させる。

［補足］現在の実装では、SoLoud 内蔵の miniaudio バックエンドをデバイス出力に使い、テストには null バックエンドを使う。
空間音源は、音源ごとに Steam Audio の直接音処理と HRTF を適用してから SoLoud に渡す。
処理済みの音声に `play3d()` を重ねず、二重の定位・減衰を避ける。

［補足］WAV／Ogg／MP3 のデコード・ストリーミング、HRTF、遮蔽、再生終了を検証している。
壁メッシュによる遮蔽・材質別の透過と、部屋の反射音生成もテストで確認した。
ただし、実ゲームでの移動音源・リスナー追従、音響メッシュの連携、反射バス、バックグラウンド計算やベイク用ツールは未実装である。
反射音の確認は検証用シーンに対するものであり、ゲーム側への統合完了を意味しない。

## 7. 依存管理・フォーク・ビルド

### 7.1. リポジトリ構成

このプロジェクトで使う依存は、兄弟リポジトリを必須とせず、`third_party/` 配下の Git submodule として保持する。
親リポジトリが依存のコミットを固定し、通常のビルドで自動追従させない。

OGRE Next は独自の変更を加える見込みがあるため、本家を直接の参照先とせず、ユーザーのフォークを使用する。
参照先は `git@github.com:SAM-tak/ogre-next.git`、開発ブランチは `throne-dev` とする。

［補足］submodule の通常の取得はブランチの先端ではなく、親が記録したコミットを使う。
`throne-dev` はフォークでの開発先であり、未検証の変更を自動取得する指定ではない。
L^ も標準では固定した submodule を使用し、言語自体の開発時には明示的に兄弟チェックアウトを指定できる構成にしている。

### 7.2. ソースビルドと SDK

［補足］現在の依存管理では、Steam Audio は例外として、公式 C SDK 4.8.1 の配布物をバージョンと SHA-256 で固定取得する。
既存 SDK を指定する経路も用意している。Steam Audio のソースをこのプロジェクト内でビルドする構成ではない。

Vulkan SDK のインストールはユーザーが行い、セットアップではその場所を指定して描画側をビルドした。

［補足］Vulkan を使うプログラムすべてが、開発時に SDK の手動インストールを要求するわけではない。
LÖVE／megasource との比較では、ヘッダーやシェーダーコンパイラーなどを依存として持つ構成も確認した。
Ogre Throne では、現在は Vulkan SDK のヘッダー・ローダーライブラリを使い、glslang は固定ソースからビルドする。
OGRE が glslang の C++ API を直接使うことと、Debug／Release・CRT を揃える必要から、この構成になった。

### 7.3. Windows のコンパイラー

Windows でも Clang を標準とし、MSVC を互換性確認用に残す。

［補足］最初のセットアップは MSVC で行った。その後、Windows でも Clang を使う方針が明示され、切り替えた。
他 OS とコンパイラー系統を揃え、診断や言語処理の差を減らすことを利点として整理した。
実行速度やビルド時間が常に MSVC より優れる、という測定結果に基づく決定ではない。

［補足］具体的な構成は `clang-cl` ＋ Ninja Multi-Config とする。
MSVC ABI、Windows SDK、MSVC の標準ライブラリを利用し、ソースビルドする依存の CRT は `/MT`／`/MTd` で揃える。
Clang 本体は導入済みだったが、ClangCL 用 MSBuild ツールセットが未導入だったため、Ninja を使用した。
MSVC 側は Visual Studio 生成器を使い、別ビルドディレクトリに分離する。

［補足］切り替えに際して OGRE フォークへ clang-cl 互換修正を加えた。
内容は SIMD 演算子、制限付きポインター配列、Windows リソースのオプション、初期化、PBR の整数変換などである。
OGRE が無限大を境界表現に使用するため、Clang 側の浮動小数点設定は `/fp:precise` とした。
Box3D では FMA contraction の抑制も維持している。

［補足］Clang の Debug／Release で全 3 テストと Vulkan 起動を確認した。
MSVC の互換性確認用ヘッドレス構成でも全 3 テストを確認し、CI に両コンパイラーの検証設定を追加した。
Linux／Apple での実機検証や、CI のリモート実行を完了したという記録ではない。
